# Найденные ошибки

Список составлен по итогам ручного и автоматического аудита проекта (бэкенд + фронтенд): статический анализ (ruff, tsc, biome), полный прогон тестов, живой e2e-запуск через Docker/uv/npm и проверка в браузере. Каждый пункт воспроизведён и подтверждён, не догадка.

## Критично

### 1. `POST /api/v1/routes/` и `POST /api/v1/chat/` не требовали авторизации
Оба эндпоинта были доступны без токена — в отличие от `/api/v1/items/`, где авторизация была. Подтверждено реальным запросом: маршрут создавался в базе без единого токена.
- Файлы: `backend/app/api/routes/routes.py`, `backend/app/api/routes/chat.py`
- Риск: кто угодно мог насыпать записей в БД и молотить публичный OSRM-сервер через бэкенд; `/chat/` мог использоваться для бесконтрольного расхода платного API OpenAI/Groq.
- **Статус: исправлено** (добавлена зависимость `CurrentUser`).

### 2. `/chat/` не имел rate-limiting
Ничто не ограничивало количество запросов к платному LLM API на одного пользователя.
- **Статус: исправлено** (добавлен `backend/app/core/rate_limit.py` — in-memory sliding-window лимитер, 10 запросов/60 сек по умолчанию, настраивается через `.env`).
- Оговорка: лимитер процесс-локальный, не будет работать корректно при нескольких репликах бэкенда без переноса на общее хранилище (Redis).

### 3. Скрытый баг в миграции `create_route_table.py` — GiST-индекс на TEXT-колонке
Миграция пыталась создать пространственный индекс (`GIST`) на колонке `route_geometry`, которая на самом деле объявлена как `TEXT`, а не как PostGIS `geometry`. GiST не имеет дефолтного operator class для текста — попытка создания индекса гарантированно падает и убивает всю транзакцию миграции (даже несмотря на `try/except` в Python — PostgreSQL необратимо помечает транзакцию как aborted при первой же ошибке SQL).
- Баг был **спящим 5 дней**, потому что PostGIS реально никогда не подключался (см. пункт 4) — ветка кода с индексом просто не выполнялась.
- Воспроизведено напрямую в psql: `ERROR: data type text has no default operator class for access method "gist"`.
- Файл: `backend/app/alembic/versions/create_route_table.py`
- **Статус: исправлено** — битый индекс убран, добавлен комментарий с объяснением; поле снова помечено как "зарезервировано под будущий нативный geometry-тип".

### 4. Фронтенд полностью сломался после включения авторизации на `/routes/` и `/chat/` (регрессия, найдена и исправлена в этой же сессии)
После добавления `CurrentUser` на бэкенде три места на фронтенде не отправляли токен и/или использовали неверный базовый URL, из-за чего фичи молча деградировали:
- `frontend/src/components/Chat/AIChat.tsx` — сырой `fetch("/api/v1/chat/")` без заголовка `Authorization` и без базового URL (относительный путь работает только когда фронт собран и раздаётся бэкендом с того же origin; в dev-режиме на `:5173` бьёт в никуда).
- `frontend/src/lib/routesApi.ts` (`callBackend`) — тоже без `Authorization`. Из-за этого страница `/routes` молча проваливалась в "демо-режим" (прямой вызов публичного OSRM из браузера, в обход своего бэкенда), не сообщая пользователю, что бэкенд на самом деле недоступен из-за 401, а не потому что офлайн.
- `frontend/src/routes/_layout/routes.tsx` — `API_BASE_URL` был захардкожен как `"http://localhost:8000"` вместо `VITE_API_URL`, который используется во всём остальном приложении (`main.tsx`, сгенерированный API-клиент). При других портах/окружениях это тихо расходится с реальным адресом бэкенда.
- **Статус: исправлено** во всех трёх местах, живьём проверено в браузере (авторизованный `/chat/` получает честный 500 из-за отсутствия Groq-ключа вместо 401; `/routes` показывает "● бэкенд на http://..." вместо "демо-режим").
- Обнаружено попутно: у `/chat/` вообще нет тестового покрытия (`tests/` не содержит `test_chat.py`).

## Средне

### 5. "MCP" в названиях — вводящая в заблуждение терминология
Код и README называли обычный OpenAI/Groq function-calling "MCP" (Model Context Protocol) и "MCP-сервером". Реального MCP-протокола (JSON-RPC, MCP-сервер/клиент) в проекте нет — `route_tools.py` — это просто функция, вызываемая LLM через стандартный tool-calling API, которая сама делает HTTP-запрос на свой же `localhost:8000`.
- Файлы: `backend/app/tools/route_tools.py`, `README.md`
- **Статус: исправлено** — переименовано в "LLM function calling" / "tool calling" с явной пометкой "not MCP".

### 6. PostGIS заявлен в документации, но не подключён в `compose.yml`
`compose.yml` поднимал голый `postgres:18` вместо PostGIS-образа. README и `ARCHITECTURE.md` утверждали "PostGIS для хранения геометрии маршрутов", хотя расширение никогда не создавалось, и миграция тихо откатывалась на хранение геометрии как `TEXT`.
- **Статус: исправлено** — образ заменён на `postgis/postgis:16-3.5` (реально доступный, PostGIS 3.5.2 подтверждён командой `\dx` после миграции), volume путь скорректирован под новый образ. Документация приведена в соответствие с реальностью: колонка `route_geometry` до сих пор `TEXT`, а не нативный `geometry`-тип — это явно прописано как известное ограничение, а не выдано за готовую фичу.

### 7. Неполное HTML-экранирование в `JsonPanel.tsx`
Подсветка синтаксиса JSON в UI использовала `dangerouslySetInnerHTML` с экранированием только `&` и `<`, без `>` и кавычек. Сейчас поля ответа API — только числа и даты, поэтому эксплуатация невозможна на практике, но это готовая XSS-дыра на случай появления в ответе любого текстового поля.
- Подтверждено тестовым payload'ом `<img src=x onerror=alert(1)>` — после фикса рендерится как безопасный текст, а не как исполняемый тег.
- Файл: `frontend/src/components/Routes/JsonPanel.tsx`
- **Статус: исправлено** — экранируются все 4 HTML-спецсимвола (`&`, `<`, `>`, `"`) до применения подсветки.

### 8. `useCountUp` — эффект бесконечно перезапускал сам себя
Хук анимации чисел (используется в `StatsPanel`) включал `current` (state, который сам же обновляет) в зависимости `useEffect`. Каждый вызов `setCurrent` внутри интервала перезапускал сам эффект, из-за чего анимация не считала линейно за заданную `duration`, а асимптотически приближалась к цели и **никогда не завершалась** — `setInterval`/`clearInterval` пересоздавался ~60 раз в секунду бесконечно, пока смонтирован компонент (лишняя нагрузка на CPU, утечка таймеров).
- Подтверждено симуляцией в Node: после 50 "перезапусков" значение равно 74.1 вместо честных 100 — то есть `progress === 1` никогда не достигается.
- Файл: `frontend/src/hooks/useCountUp.ts`
- **Статус: исправлено** — стартовое значение читается через `useRef`, а не через сам управляемый state, `current`/`decimals` убраны из зависимостей эффекта.

## Мелкие / формальные (biome, ruff)

### 9. Мёртвый `@ts-ignore` в `chat.tsx`
Подавлял несуществующую ошибку типов — `tsc` проходит и без него.
- **Статус: исправлено** — удалён.

### 10. Прочие находки линтеров (не исправлялись, низкий приоритет)
- `lint/a11y/useButtonType` — несколько `<button>` без явного `type` (`PresetChips.tsx`, `CoordForm.tsx`, `JsonPanel.tsx`, `AboutPanel.tsx`) — риск случайной отправки формы.
- `lint/a11y/noLabelWithoutControl` — `<label>` без связанного поля ввода в `CoordForm.tsx`.
- `lint/suspicious/noShadowRestrictedNames` — `AppSidebar.tsx` импортирует иконку с именем `Map`, затеняющую глобальный `Map`.
- Неотсортированные импорты, f-строки без плейсхолдеров (`groq_provider.py`, `openai_provider.py`), неиспользуемый импорт `json` в `openai_provider.py` — косметика, не влияет на поведение.
- Отсутствие форматирования (табы/точки с запятой) в нескольких компонентах — `biome check --write` чинит автоматически.

## Не ошибка, но стоит знать

- `route_geometry` в таблице `route` остаётся `TEXT`, а не нативным PostGIS `geometry`-типом — реальные пространственные запросы (расстояние, пересечения) сейчас невозможны средствами БД, несмотря на подключённый PostGIS.
- Лимитер чата (`rate_limit.py`) не переживёт горизонтальное масштабирование бэкенда на несколько процессов/реплик без переноса состояния в общее хранилище.
- У `/chat/` нет автотестов — вся проверка была сделана вручную через браузер и curl.
